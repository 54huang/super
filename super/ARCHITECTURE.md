# 架构

这个仓库要解的问题不是"存文件"，而是：**半年后回来，还能看懂当时为什么这么做，并且能验证它没坏。**

所以分成五层，依赖方向严格单向。

---

## 一、五层

```
        library/            campaign/            renderer/
      （研究资产）          （生产资产）          （实现资产）
           │                    │                    │
           └────────┬───────────┴──────────┬─────────┘
                    ▼                      ▼
                 specs/  ◄──────────── tests/
              （契约层，机器可读）    （证据层，会失败的断言）
                    ▲
                    │
                 docs/  （决策与流程：为什么这样做）
```

| 层 | 目录 | 职责 | 不允许做的事 |
|---|---|---|---|
| 研究资产 | `library/` | 外部知识的结构化索引：来源、用途、取用路径 | 不写实现细节，不放代码 |
| 生产资产 | `campaign/` | 一条具体片子的全部档：文案、分镜、提示词、验收 | 不放通用规则（通用规则属于 library 或 specs） |
| 实现资产 | `renderer/` | 可运行的渲染器 | 不硬编码分镜数据（应从 specs 读或与 specs 对齐） |
| 契约层 | `specs/` | 机器可读的事实：分镜、Schema、设计令牌 | 不描述"想法"，只描述"事实" |
| 证据层 | `tests/` | 把契约变成断言 | 不测"好不好看"（测不了就别假装测） |

**关键约束**：`specs/` 不依赖 `renderer/`，`library/` 不依赖任何层。所以可以单独替换渲染器实现、单独扩充素材库，互不影响。测试是唯一同时看见三者的地方——它负责保证它们说的是同一件事。

---

## 二、为什么分三层资产，而不是一个大文件夹

如果混在一起，会稳定地出现三个问题，这三个问题我都见过太多次：

1. **找不到**：素材（50 个外部仓库）和产出（一条片子）混排，搜索"运镜"会同时命中"某个仓有运镜词表"和"我们这条片子在 8 秒用了推镜"，两者用途完全不同。
2. **说不清来源**：素材是别人的，产出是自己的。混放之后，半年后没人分得清哪句话是抄的、哪句话是判断。
3. **改不动**：换美术方向时，要改的是"实现 + 提示词 + 分镜描述"三处，如果它们分散在十个目录，必然漏掉一处，然后画面和文档打架。

分层之后各自有稳定的边界：`library/` 是**输入**，`campaign/` 是**这次的处理结果**，`renderer/` 是**这次用到的机器**。

---

## 三、为什么事实要写成 JSON（specs）

`campaign/30s-raii/2_分镜表.md` 是给人看的，`specs/shots.json` 是给测试和渲染器看的。两者必须一致，不一致时以 JSON 为准并回头改 Markdown——因为 JSON 有测试守着。

事实类的东西（时长、时间码、安全区、色值、字号、缓动）一律进 `specs/`，因为：

- 它们**可以被断言**（时间码闭合、字数上限、色值漂移）；
- 它们**会被多处引用**（渲染器、提示词、验收清单都依赖同一批数字）；
- 它们**会过期**（星数、平台档位），集中一处才好批量更新。

判断类的东西（为什么选这个美术方向、为什么这镜交给代码）进 `docs/decisions/`，因为判断不能断言，只能解释。

---

## 四、为什么三镜交给代码而不是 AI

不是因为代码更"高级"，而是因为这三种画面**AI 无法保证正确性**：

| 画面需求 | AI 生成的失败方式 | 代码渲染的保证 |
|---|---|---|
| 真实可读的 C++ 代码 | 必然写成乱码 | 它就是字符串，一定对 |
| 落章在精确位置、震 1.4px、60ms | 抖动幅度与时机不可控 | 参数化，逐帧可复现 |
| 自由落体穿过三层、每层盖章 | 物理不对、穿层时序乱 | t² 落体 + 区间判断，时序精确 |
| 栈/堆结构图的层级关系 | 结构必然画错 | 坐标写死，不会错 |

反之，S01/S02/S04/S07 这类"氛围向 + 转场"的镜头交给 AI 更省力——代码画光效很生硬。**分工依据是"正确性要求"，不是"技术偏好"**（详见 ADR-003）。

## 五、扩展方式

### 加一个素材仓

1. 在 `library/<分类>/README.md` 的表格里加一行（编号接着排）；
2. 更新 `library/00_起点/全仓清单.md`；
3. 在 `docs/research/repos.snapshot.json` 的 `repos` 数组里加一条（id 接着排）；
4. 若标记为节点，在对应目录加 `Nxx_仓库名.md`，并登记到 `library/00_起点/节点总表.md`；
5. `npm test` —— 数量、编号连续性、节点文件存在性会自动核对。

### 加一条新片子

1. 复制 `campaign/30s-raii/` 为 `campaign/<新项目>/`；
2. 写 `specs/<新项目>.shots.json`（沿用 `specs/shots.schema.json`）；
3. 测试里把 spec 路径参数化后即可复用全部断言；
4. 分流生产：`producedBy: "ai"` 的镜头走提示词，`"code"` 的镜头进 `renderer/`。

### 换美术方向

1. 在 `specs/style-tokens.json` 改调色板与层序；
2. 改 `renderer/src/shot-renderer.js` 顶部常量；
3. `npm test` 会告诉你两边是否漂移（`tokens.test.mjs`）；
4. 在 `docs/decisions/` 补一篇 ADR，写清为什么换、换了什么、代价是什么；
5. 旧方案不要删，标 `status: legacy` 留档（`renderer/legacy/` 里就是这么做的）。

## 六、已知的架构债

诚实列出来，比假装没有好：

- `tests/` 目前硬编码指向 `30s-raii` 的 spec，加第二条片子时需要参数化。
- 渲染器的 `SHOTS` 时长与 `specs/shots.json` 是**两份数据靠测试对齐**，理想状态是渲染器直接读 JSON（但会让 `file://` 打开失效，权衡后选择前者）。
- 素材库的星数快照没有自动刷新机制，只是记录了日期和复查方法。
- 视觉观感无自动化验证——这是当前最大的空缺，见 `docs/verification.md`。
