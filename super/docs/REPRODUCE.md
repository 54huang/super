# 可复现手册：从一句文案到 30 秒竖屏片

这份文档的目的只有一个：**换一个人，照着做，能得到同等质量的产出。**

和 [PROCESS.md](../PROCESS.md) 的分工：那份讲"为什么这么做"（方法论），这份讲"具体怎么做"（操作手册）。有冲突时以这份为准，因为它是按最后一次真实出片校准的。

---

## 零、先纠正一张图

流传的链路是四段：

```
GitHub 素材节点库 → Canvas 风格/画面约束 → FFmpeg 合成 → TTS 配音
```

**这条链有四处不对，其中两处会直接导致做不出来。**

实际跑通的链路是七段（**不含配音**——见文末「后续优化」）：

```
① 定边界 ──→ ② 写口播稿 ──→ ③ 切镜分镜 ──→ ④ 选美术方向
   (平台/时长)   (字数定时长)    (时间码定结构)    (色板/字体/线宽)
                                                        │
                                                        ↓
                 ⑧ 验收 ←── ⑦ 合成 ←── ⑥ 渲 900 帧 ←── ⑤ 写渲染器 + 锁契约
                              (ffmpeg)
```

四处偏差：

| 偏差 | 实际情况 |
|---|---|
| **素材库不在产线上** | `library/`（50 仓 / 24 节点）与渲染器**零引用**——`grep -r "library/" --include="*.js"` 只命中一句注释。它产出的是方法，不是素材文件。想复现出片，**不需要先收集 50 个仓库** |
| **少了最要命的两步** | 口播稿和分镜。字数决定时长，时间码决定结构。跳过这两步，后面全是空中楼阁 |
| **TTS 不是最后一环** | 配音不在本流程内（列为后续优化），但口播稿仍排在 ②——它是时长的**来源**，不是收尾动作。先出画面再想配音，必然重排时间码 |
| **少了验证环** | 这套方法的命门是契约测试。没有它，改一处参数画面就漂移，而你不知道 |

## ① 定边界

先写死三个数，后面所有环节都受它们约束：

| 项 | 本片取值 | 为什么是这个数 |
|---|---|---|
| 画幅 | 1080×1920（9:16） | 竖屏平台标准 |
| 帧率 | 30 fps | 900 帧正好 30.000 秒，无残差 |
| 总时长 | 30 秒 | 单镜必须落在 4/6/8/10 秒档位，加起来正好 30 |

产出：写进 `specs/shots.json` 的 `format` 段。

验收：`width × height × fps × totalSec` 四个数能推出帧数 900，且 900 ÷ 30 = 30.000 无余数。

---

## ② 写口播稿（最关键的一步）

**旁白先存在，镜头时长才不是编出来的。**

```
125 字 ÷ 30 秒 ≈ 4.2 字/秒     （讲解类舒适区 3.8–4.5，低于 3.8 显得拖，高于 4.5 听不清）
```

结构用七拍：钩子（反问）→ 举证 → 制造缺口 → 反转 → 机制 → 命名 → 结论。

产出：`campaign/30s-raii/1_口播稿与SRT.md`，含口播稿正文 + 标准 SRT + 时间码校验表。

验收：

- 总字数 ÷ 目标时长 落在 3.8–4.5
- 7 条字幕合计正好 30.000 秒，无空洞无重叠
- 每条字幕 ≤16 字符（不含空格）——竖屏一行放不下更多
- 断句在语义停顿处，不跨镜断

**最容易错**：先想画面再配音。画面是为旁白服务的，反过来会得到一堆漂亮但听不懂的镜头。如果念完是 28.4 秒，多出的 1.6 秒**不要摊给七个镜头**，要么把收尾镜延长到档位，要么删一句冗余的话。时间码是硬约束，画面是软约束。

---

## ③ 切镜与分镜表

按**时间码**切，不是按字数、不是按感觉。时长必须贴着平台档位取整。

本片结果：`4 + 4 + 4 + 4 + 6 + 4 + 4 = 30.000`

产出两份，说的是同一件事：

| 文件 | 给谁看 |
|---|---|
| `campaign/30s-raii/2_分镜表.md` | 人读：景别 / 机位 / 运镜 / 功能 / 字幕 + 节奏检查 |
| `specs/shots.json` | 机读：给测试和渲染器用的事实源 |

验收（`tests/storyboard.test.mjs` 自动核对）：

```bash
node --test tests/storyboard.test.mjs     # 只跑分镜契约，约 70ms
```

- 时间码闭合：0→30 无缝、不重叠、不留空
- 每镜时长在 4/6/8/10 内
- 每 8 秒内至少一次视觉变化（景别或时长切换）
- 写"5.5 秒"这种时长会直接判错——平台会吸到 6 秒，音画立刻错位

---

## ④ 选美术方向

先挑风格，再谈实现。从 `docs/cases/` 里选一张现役卡（02 制图台 / 03 示波器），**把它末尾的「风格引导块」整段抄成常量**，不要边画边调。

引导块是这张卡唯一"能拿走"的部分：喂给 AI 就是风格提示，落成代码就是常量表。判断标准写在各卡的「什么场合用／别用」里——选错了方向，后面每一帧都在跟风格打架。

本片用案例 02「制图台」：

| 约束 | 取值 |
|---|---|
| 纸底 | `#F4EFE3` → `#E3D9C4` 渐变 |
| 细格 / 粗格 | 36px α0.045 / 180px α0.10 |
| 墨线 | `#1B1A17`，线宽 2.5 / 1 / 1 / 1.2 / 3 |
| 强调色 | 朱红 `#BE3A2B`，**面积 ≤3%** |
| 字号 | 52 / 25 / 20 / 17 / 13 / 11，最多 6 级 |
| 字体 | 标题思源宋体 400/700，代码 Consolas，等宽栈必须显式写中文字体 |

验收：色值、线宽、字号全部出现在源码里，并且有断言盯着不漂移（`tests/tokens.test.mjs`）。

**最容易错**：先挑好看的色再想语义。朱红在这个体系里只代表"批改/否定"，一旦拿去当装饰色，整套视觉的语义就废了。

## ⑤ 写渲染器 + 锁契约

渲染器的铁律：**同一个 `t` 必须画出同一帧。** 所有随机量用固定种子的 `mulberry32`，噪声用 `sin(t·137.5)` 叠加，禁止 `Math.random`。

```js
const TOTAL = 30000;                 // 全片毫秒数
state.mode = 'full'                  // 全片模式
renderAt(ms)                         // 脱离动画循环，定点渲染某一毫秒
```

契约测试锁死四件事（`npm test`，当前 52 项）：

| 锁什么 | 在哪 |
|---|---|
| 七镜与分镜表逐镜对齐（数量/编号/起始秒/时长/铺满） | `tests/renderer.test.mjs` |
| 同一 `t` 两次渲染绘制序列完全一致 | 同上 |
| 设计令牌不漂移（色值/线宽/字号/种子） | `tests/tokens.test.mjs` |
| 900 帧连续渲染不崩 | `tests/renderer.test.mjs` |

验收：

```bash
npm test      # 必须 52 项全绿，0 fail
```

**最容易错**：不写断言，靠眼睛看。改一个色值、调一个 `lerp`，画面就漂了，而你要等到出片那天才发现。反向验一次：把某镜的 `from` 改 1 秒，测试必须立刻变红——不红说明断言是假的。

## ⑥ 离线渲 900 帧

不用开浏览器。用 `@napi-rs/canvas` 顶替浏览器 Canvas，`shot-renderer.js` **一行不改**跑在 Node 里。

```bash
npm i -D @napi-rs/canvas          # 或 NAPI_CANVAS_PATH 指向已有安装

# 先渲一帧对眼睛
node scripts/render-offline.mjs --frame 18000 --out check.png

# 再渲全片
node scripts/render-offline.mjs --all --out frames
```

本片实测：**900 帧 / 5 分 27 秒 / 1609 MB PNG**，单帧约 370ms。

验收：`ls frames | wc -l` 等于 900，文件数不是 899 也不是 901。

**最容易错**：以为浏览器能画中文就等于 Node 能画。**不能。** 浏览器画中文时 `monospace` 这类通用族会自动 fallback 到系统中文字体，Skia 只在字体栈内查找，栈里没有中文字体就画成豆腐块。本片真踩过：`F_MONO` 的四个候选（`ui-monospace` / `Consolas` / `Courier New` / `monospace`）一个中文字都没有，「调用来源」直接变成四个方块。修法是往栈里显式写中文字体名：

```
F_MONO  ui-monospace,Consolas,"Courier New","Source Han Serif CN","Songti SC","SimSun",monospace
```

## ⑦ 合成

```bash
ffmpeg -framerate 30 -i frames/full_%04d.png \
       -c:v libx264 -pix_fmt yuv420p -crf 16 -y raii-30s.mp4
```

本片实测：**7.0 MB**。

验收三项，缺一不可：

```bash
ffmpeg -i raii-30s.mp4 2>&1 | grep -E "Duration|Stream #"
#   Duration: 00:00:30.00                              ← 必须整 30 秒
#   Video: h264 (High), yuv420p, 1080x1920, 30 fps      ← 编码/色彩空间/尺寸

ffmpeg -i raii-30s.mp4 -f null - 2>&1 | grep -oE "frame= *[0-9]+" | tail -1
#   frame= 900                                          ← 少一帧都是错的
```

**最容易错**：只看文件生成了就当成功。`Duration 29.97` 和 `yuv444p` 都是坑——前者说明时间基不对，后者很多平台不认。

## ⑧ 验收

单镜检查 6 项、全片检查 6 项，清单在 `campaign/30s-raii/4_出片与验收清单.md`。

自动能查的都在 `npm test`；查不了的（好不好看、节奏闷不闷）必须人眼看。**"900 帧 0 异常"不等于"画面好看"**——前者是断言，后者是判断。

## 最小复现路径

如果目标只是**复现出片**，不是为了研究素材库，那 ①②③④⑤⑥⑦ 就够，**不需要碰 `library/`**：

```bash
git clone <repo> && cd super && npm test          # 确认基线 52 项全绿

node scripts/render-offline.mjs --all --out frames           # 约 5.5 分钟
ffmpeg -framerate 30 -i frames/full_%04d.png \
       -c:v libx264 -pix_fmt yuv420p -crf 16 -y out.mp4      # 约 30 秒

ffmpeg -i out.mp4 2>&1 | grep Duration            # 必须是 00:00:30.00
```

不用装浏览器，不用点 900 次下载，不用先收集 50 个仓库。

## 哪些能省，哪些不能

| 环节 | 能省吗 | 代价 |
|---|---|---|
| ① 定边界 | **不能** | 画幅帧率时长不定，后面每个数都是猜的 |
| ② 口播稿 | **不能** | 省了它就是"先画再配"，必然重排 |
| ③ 分镜表 | **不能** | 省了镜头时长会互相打架 |
| ④ 美术方向 | 能换，不能没有 | 没有方向就是每镜各画各的，拼起来像七个片子 |
| ⑤ 契约测试 | 小样可省，量产后必须 | 省了改一处漂一片 |
| ⑥ 离线渲染 | 能换成浏览器导出 | 900 次下载要点 40 分钟，且不能脚本化 |
| ⑦ ffmpeg 合成 | **不能** | 没有别的路能出 mp4 |
| 配音（不在本流程内） | 本版不做 | 当前成片无声，完播率大约砍半 |
| 素材库收集 | **能省** | 它产出方法，不产出素材。复现出片完全不需要 |

## 质量关键数字

复现时拿这张表对，任何一项偏了，产出就不会是同一水准：

| 项 | 值 | 偏了会怎样 |
|---|---|---|
| 语速 | 4.2 字/秒（3.8–4.5） | 太快听不清，太慢拖沓 |
| 单镜时长 | 4 / 6 / 8 / 10 秒 | 平台吸附，音画错位 |
| 单条字幕 | ≤16 字符 | 竖屏一行放不下 |
| 强调色面积 | ≤3% | 超过就从"批注"变成"贴纸" |
| 字号层级 | ≤6 级 | 超过就没有层级感 |
| 渲染耗时 | 约 370ms/帧 | 超过 1 秒说明有 shadowBlur 之类的重操作 |
| 码率 | CRF 16 | 更低会糊，更高体积翻倍 |
| 帧数 | 正好 900 | 少一帧时长就不对 |

## 后续优化：配音与混流

**不在上面的七段里，当前成片是无声的。** 这一段先记着怎么做，将来补。

有利条件是 SRT 时间码在 ② 就写死了，七条正好铺满 30 秒，配音只需要"填进去"，不需要重排结构。

```bash
# 1. 逐句合成，不要整段合成——整段出来没法按镜头对齐
edge-tts --voice zh-CN-YunxiNeural --text "你以为析构函数只清内存？" --write-media s01.mp3

# 2. 量每句真实时长，和分镜时间码比对
ffmpeg -i s01.mp3 2>&1 | grep Duration

# 3. 时长对不上时优先调语速重合成，不要剪音频（剪会把字切断）
edge-tts --voice zh-CN-YunxiNeural --rate=+8% --text "..." --write-media s01.mp3

# 4. 混流
ffmpeg -i raii-30s.mp4 -i voice.wav -c:v copy -c:a aac -b:a 192k -shortest out.mp4
```

对齐规则：每句必须落在自己那一镜的时间窗内。差 0.2 秒以内用首尾静音补/裁；超过 0.5 秒就调 `--rate` 重合成。

验收：`ffmpeg -i out.mp4` 能看到视频流 900 帧 + 音频流 30.0 秒，第 3、5 句起音落在 8.0s 和 16.0s 附近。

本机现状：Python 3.13 与 pip 都在，`edge-tts` 未装（`pip install edge-tts`）。
