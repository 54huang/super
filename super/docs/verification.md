第 40 项的验法——不是只看 `-version`，而是拿项目里那条真命令跑一遍再核产物：

```bash
# 造 30 帧 1080×1920 测试序列，尺寸与成片一致
ffmpeg -f lavfi -i "testsrc2=size=1080x1920:rate=30:duration=1" -frames:v 30 "S05_%04d.png"

# 原样照抄 README 的合成命令
ffmpeg -framerate 30 -i "S05_%04d.png" -c:v libx264 -pix_fmt yuv420p -crf 16 -y s05.mp4

# 核产物
ffmpeg -i s05.mp4 2>&1 | grep -E "Duration|Stream #"
ffmpeg -i s05.mp4 -f null - 2>&1 | grep -oE "frame= *[0-9]+" | tail -1
```

期望：`Duration: 00:00:01.00`、`h264 (High) … 1080x1920 … 30 fps`、`frame= 30`。实测完全一致。

**这一项仍不等于画质已验。** 它证明的是「参数组合能跑通、产物属性正确」，不证明「900 张真帧合出来好看」。真帧的观感依旧要靠人眼，见下一节。

一个观察：**v1 的测试全绿，但 v1 是"错"的**——因为它错在审美判断，而不是工程正确性。测试守得住一致性，守不住品味。品味只能靠人给反馈（"太普通了"），然后由人把反馈翻译成参数。

第二个观察：**测试的保护范围本身也会腐坏。** 原来的断链检查只认标准 markdown 链接语法（方括号里放文字、圆括号里放路径），于是所有用反引号写的路径都在保护之外。「渲染器/index.html」「campaign/02_分镜表.md」「00_起点/节点总表.md」这些旧路径就这样在文档里烂了好几轮，而 34 项断言仍然全绿。

补上第 22 项之后一次抓出 7 处，其中一处是真实断链——`renderer/README.md` 里指向逐镜提示词文件的相对路径，在渲染器移出 campaign 时没跟着改。

**断言的数量不等于覆盖的完整。** 34 项和 36 项的区别不在数字，在于后 2 项管的那片区域此前根本没人看。

第三个观察：**断言守得住"缺了"，守不住"多了"。** v4 的 12 项里有"所有文字都画在板面之内"这一条，能拦住 v2 那种掉字的裁切缺陷；但脏污开关写反之后多出来的两条横带、`cleanPatch` 亮出来的方形补丁、注释窗口算出负值——三样都在断言全绿的画面上。原因很直白：断言检查的是"该有的在不在、该在的地方对不对"，而这三样都是**不该有的东西出现了**，没有哪条断言在数"画面里出现过几次擦痕"。

补的办法不是再加断言，而是加一步**出帧看图**。这次是拿 `render-offline.mjs` 导出关键帧 PNG，逐张放大看——成本是每张 130ms，收益是三处缺陷全在这一步被抓到。断言和眼睛管的是两片不同的区域，谁也替不了谁。

第四个观察：**反向验证里"没红"有两种原因，必须分开看。**

v5 那次故意改坏 6 处，5 处红、1 处没红。没红的那处是"往源码里塞一句 `Math.random`"，按理必红——查下来不是断言弱，是**替换锚点写错了**：文件头是 `(function () {`，我按 `(function (global) {` 去替换，一个字也没改到，跑的还是原文件。

这两种情况看起来一模一样，但一个是"保护失效"，一个是"操作没生效"。区分办法只有一个：改完先确认**文件真的变了**（看 diff，或断言那一行确实存在），再跑测试。否则"绿"到底是保护有效、还是根本没测，说不清。

配套一条：那次还换掉了一条断言——它算"旁白字数 ÷ 总时长"。实测下来它既拦不住真问题（稿子超长 20% 照样绿），又会误伤正常稿子（短句多、停顿多时字数密度天生偏低）。**能测产物就别测估算**：字数估出来的秒数不是秒数，配音对齐表里的秒数才是。
