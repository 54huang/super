# ADR-003 · 三个镜头交给代码渲染，而不是 AI 生成

**状态**：已采纳（2026-10-28）

## 背景

一条 30 秒片子里有 7 个镜头。最初的方案是全用 AI 生成（Seedance / 即梦），提示词写在 `campaign/30s-raii/3_逐镜提示词.md`。

问题出现在三个镜头上：

| 镜头 | 画面要求 | AI 的实际表现 |
|---|---|---|
| S03 异常 | 画面上有**真实可读**的 C++ 代码，红笔划在第 3 行 | 代码必然乱码；红笔位置随机 |
| S05 作用域 | 主体自由落体穿过三层，每层盖一枚章，落地碎裂 | 物理不对（飘、慢动作过头）；穿层时序乱 |
| S06 结构 | 栈/堆两栏关系图，中线标 lifetime | 结构必然画错、线条扭曲 |

这三个镜头的共同点：**画面里有"必须正确"的信息**。AI 生成的是"看起来像"的东西，而这几个镜头要的是"就是对的"。

## 决定

按**正确性要求**而不是技术偏好分流：

- `producedBy: "code"` → S03 / S05 / S06：用 Canvas 逐帧渲染，坐标与时间写死；
- `producedBy: "ai"` → S01 / S02 / S04 / S07：氛围向与转场，AI 更省力且质量更高。

判据写进 `specs/shots.json` 的 `producedBy` 字段，测试会检查 code 镜头在渲染器里确实存在。

## 后果

- **收益**：三镜从"抽卡 6 次不一定对"变成"一定对"。代码、结构图、物理时序这类内容，代码的正确率是 100%，AI 是 0%。
- **收益**：可逐帧导出，同一时间点永远同一张图（见 ADR-005），后期要改一句代码重渲染即可，成本接近零。
- **代价**：写实能力为零——四个 AI 镜头无法用代码替代，只能混剪。
- **代价**：维护两套产线。缓解方式：把分流判据写成表格（`PROCESS.md` 第 6 步），并让 `producedBy` 成为规格的一部分，而不是口头约定。
- **代价**：需要 Node 环境才能预览/导出。用零依赖的本地服务和纯 HTML 单页降低门槛。
