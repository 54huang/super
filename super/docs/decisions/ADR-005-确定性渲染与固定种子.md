# ADR-005 · 确定性渲染与固定种子（而不是 CSS 动画或录屏）

**状态**：已采纳（2026-10-28）

## 背景

要给三个镜头出片，有三条路：

1. **CSS/Web 动画 + 录屏**：写起来最快，但录屏受浏览器帧率影响，掉帧就废；
2. **CSS 动画 + 逐帧截图**：要控制动画停在某一帧，`animation-play-state` 与 `steps()` 配合极其别扭；
3. **Canvas + 时间驱动的渲染函数**：`render(t)`，画面完全由 `t` 决定。

## 决定

选第三条。具体约束：

- 所有绘制由 `render(t)` 完成，**没有内部状态**，同一个 `t` 必须产出同一帧；
- 所有随机用 `mulberry32` **固定种子**（`specs/style-tokens.json` 的 `rendererContract.seeds` 里登记了 5 个），不用 `Math.random`；
- 噪声纹理（纸颗粒）只生成一次并缓存为 pattern，避免每帧重算导致闪烁；
- 逐帧导出走 `canvas.toDataURL('image/png')`，文件名带帧号，交给 ffmpeg 合成。

## 后果

- **收益**：可逐帧导出、可任意定位、可断点续渲。改一个参数重渲，只影响该参数，不引入新随机。
- **收益**：**可测试**。`tests/renderer.test.mjs` 会渲染同一 `t` 两次并比对完整绘制调用序列——如果引入了 `Math.random` 或状态泄漏，测试会立刻变红。这是录屏方案根本做不到的。
- **代价**：所有动画必须手写缓动（`easeOutExpo` / `backOut` / t² 落体），不能用 CSS transition 的现成能力。
- **代价**：导出需要浏览器环境；Node 里只能跑桩测试（验证不崩、验证确定性），**验证不了好不好看**。这个空缺被明确记录在 `docs/verification.md`，而不是假装覆盖了。
- **代价**：性能受限于 Canvas 2D 的 fill/stroke 次数。当前 1080×1920 下每帧约 500 次调用，正常机器上 30fps 无压力；若要上 4K 需换 OffscreenCanvas 或分层缓存。
